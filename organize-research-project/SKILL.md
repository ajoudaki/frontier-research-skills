# Organize Research Projects

Give a research program durable boundaries between exploration, evidence, and
accepted dependencies. Keep its organization understandable after conversations
end and independently usable by the next contributor.

This skill owns project organization. It does not select the scientific target,
prove a result, authorize experiments, or declare research accepted. Preserve
the user's requested scope and the project's adopted rules.

## Select the relevant module

| Requested work | Read |
|---|---|
| Set up a project, adapt an existing layout, or update an adopted workflow | [Project setup](references/project-setup.md) |
| Start, resume, separate, or coordinate investigations; define reviewer inputs | [Study boundaries](references/study-boundaries.md) |
| Prepare or audit incorporation into maintained theory or code | [Promotion](references/promotion.md) |
| Organize runs, external storage, reproducibility, or figure provenance | [Reproducible artifacts](references/reproducible-artifacts.md) |

Read the modules needed for the decisions being made. A complete new workflow
needs all four; a storage correction does not require redesigning the project.

## Establish the working scope

Read the applicable project instructions and workflow before proposing changes.
Identify the requested operation: advice, new setup, bounded adaptation, study
coordination, or promotion preparation. An advice request remains read-only.

Inspect paths, ownership, Git state, and designated entry points. Metadata-only
coordination is sufficient to locate studies; do not search unrelated studies
for scientific content. Identify the owner and allowed inputs of the current
investigation before reading its findings.

Map the following roles onto existing locations before inventing directories:

- project instructions and the locally adopted workflow;
- maintained theory, shared definitions, and reusable code;
- study source and current records;
- generated runs, figures, and retained reproduction inputs;
- frozen candidates, review evidence, and accepted releases.

One location may serve several compatible roles. Preserve usable records and
existing path conventions. Ask only for a consequential choice that current
instructions and authorization do not resolve.

## Preserve the research invariants

- A study has a scientific question, permitted inputs, an owner, and an output
  namespace. A conversation is not its identity.
- Exploratory findings remain provisional dependencies until the project's
  adoption process accepts them. Scientific validity, checking, and adoption
  are distinct statuses.
- Independent work requires independent information exposure; different names,
  folders, agents, or processes do not establish independence.
- Maintained additions contain their actual arguments, reusable implementation,
  and reproduction recipes, without hidden dependence on study history.
- Figures and conclusions identify the source, inputs, configuration, and run
  that produced their evidence. A stored checksum alone cannot recover data.
- Failed, negative, and superseded investigations retain useful evidence and
  clear status. Keeping a result does not require promoting it.

## Keep responsibilities modular

Use an available specialized skill only when the actual task calls for it:

| Responsibility | Existing skill, when available |
|---|---|
| Scientific reasoning within an investigation | `formulate-problem` |
| Standalone proof work | `solve-problem` |
| Mathematical notation and presentation | `explain-canonically` |
| Teaching source material | `teach-material` |
| Reviewing an external AI paper | `review-paper` |

These skills do not replace the project's source boundaries or acceptance
policy. Their internal ledgers may be sections of the study's existing record;
do not require duplicate administrative files. Do not load every skill merely
because the project combines theory and experiments.

## Deliver the requested organization

For setup or adaptation, use the templates linked from the setup module as
starting points. Produce a self-contained local workflow with actual paths,
chosen policies, and adoption provenance. Version it in the project. Later
changes to this global skill do not silently amend that local policy.

For a bounded operation, update only the relevant existing records or rules.
Report the resulting locations, checks, unresolved dependencies, and remaining
decisions. Never present structural validation as a scientific review or launch
research merely to demonstrate the new directory layout.
