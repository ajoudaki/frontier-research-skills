So that's the strategy. But it's easier said than done. Do we need smarter models? Surprisingly, no: the models already have the capability. What's missing is the workflow around them, and it rests on four foundations. First, context. Use a coding agent, not a chat, and run it on one central, always-on machine. Then the theory, the LaTeX, the code, the results and the figures are all in reach, and you stop uploading things back and forth. Chat apps let you group threads into projects; here the repo is the project, for everything. Agents work overnight, and even if you dispatch jobs elsewhere, the results come back to that one place. Second, persistence: put everything under version control. Not just the code, which most of us already do, but the theory, the notes, the audits, the paper. When you give agents freedom, things go wrong, or you change your mind, or you want a big refactor, and you can always roll back. Third, reuse. If you type the same prompt again and again, turn it into a skill. A skill can be the default for a project, so every agent in that folder reads it; or you load it by name; or it loads itself when a task matches its description. And unlike a chat's memory, skills are plain files, so they move with you to another model. The fourth is less obvious: many agents. Not because they're faster: you pay for the tokens either way. A single thread accumulates everything: every dead end, every earlier claim, every sentiment. Once it makes an early mistake, everything after it is anchored to it, and telling it to be unbiased can't undo that. Separate agents start clean, especially if you isolate them and decide mechanically what they see. Run four, prompted for diversity. The first misses the flaw. So does the second. The third catches it. The fourth misses again. One catch is all you need: it's asking ten people instead of one person ten times. And everything in this repo is a skill built on these foundations.
