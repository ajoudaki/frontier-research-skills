# Research with AI Agents: speaker notes v2

## 1. Cover
Hi everyone, I'm Amir. I want to share how I do research with AI agents these days: what went wrong, and the hacky tactics that fixed most of it for me. None of this is a principled framework. It's practical, and everything I show is in a repo you can use, linked at the end.

## 2. The transition
We're in the middle of a transition. Not long ago, we wrote our code and our papers ourselves, line by line. Now the models are extremely smart, and the opportunity is enormous: if we could really tap into that intelligence, research would move much faster. But we haven't learned the new way of working yet. We have to learn new ways of writing theory, papers and code, and that goes for experiments as much as for proofs. From what I hear, most of us are struggling with it. I certainly was.

## 3. Why this is hard
I've used these models since 2022, first for coding, and for coding they just kept getting better. Research is different, because research fails differently. When code is wrong, you usually see it: it doesn't run, a test fails, the plot looks off. When research is wrong, it can fail miserably and still look fine. So as the models got smarter, using them for research actually got harder, and at some point I gave up and went back to pen and paper. We used to do everything ourselves, so we knew exactly what was going on. Now so much is delegated that it's easy to lose track, and to lose control.

## 4. The bottleneck becomes you
And losing track turns into the real bottleneck: you. These models produce code and theory much faster than you can read or check it. Some of it is wrong. Some of it isn't relevant. Some of it quietly answers a different question. So you end up with a huge pile of results, a few gems hidden in a haystack, and no easy way to find them. That can be overwhelming enough that you just give up. So here's the question for the rest of this talk: how do you raise the signal-to-noise ratio, so that what reaches you is worth your time, and you stay in control? Every trick I'll show is a filter on that pile. But first, a few basics.

## 5. The basics
Some of these I didn't know existed until recently. One: leave the chat window. A coding agent like Codex or Claude Code runs inside your repo, so your papers, code and results are already in context. Two: run it on an always-on workstation you connect to from anywhere. Everything lives in one place, and the agents can work overnight. Then the pieces you configure. A skill is a folder with a SKILL.md file: the agent sees only its short description, and loads the full instructions when a task needs them, or when you name it. AGENTS.md, or CLAUDE.md for Claude Code, holds the project's rules and is read at the start of every session, so keep it short. Routing: a skill can link reference files that open only when needed, so out of ten long papers, the agent loads only the one it needs. And subagents: the main agent can spawn fresh agents with a clean context, which do one job and report back. Those turn out to be the key to checking results.

## 6. Don't downgrade my question
The first filter is upstream: making sure the agents answer the right question at all. These models seem trained to solve precise problems. Give them an open question, and they find a special case, or a counterexample, or an assumption you didn't explicitly forbid, and they solve that instead. Little tweaks that kill the question. And in long threads, they drift away from it. So I split the work into two stages, with two skills. Stage one is investigate-conjectures: it turns an open question into a sharp conjecture. If your question is already precise, it freezes it as a contract the agents keep checking themselves against. If it's vague, and that's the trick I like most, the model uses its own intelligence to formulate it, faithful to the spirit of your question, with no easy escape route, and the skill checks that formulation against a list of ways to cheat, like an easier target or a weakened "for all". Stage two is solve-math-rigorously: only once the question is locked does it solve it, taking the strongest reading, never a straw man, and showing every step. That alone cuts out a lot of noise, and a lot of arguing with the model about what you meant.

## 7. Fresh audits
Once something is solved, you need to check it, and this is where subagents come in. Asking the same thread to be unbiased doesn't work. A thread that's been celebrating keeps giving you happy feedback, and a thread that's turned negative stays negative. So you don't ask for independence; you enforce it mechanically. You spawn a new agent, so it doesn't carry the long thread. But fresh isn't enough: if it can read your earlier notes saying "this is a great result", it's biased all over again. So each auditor gets a folder with only the files it should see. Then I use several, each from one angle: one re-derives the math, one tests the code or reruns the experiment, one checks the literature and whether citations are used correctly, and one asks whether we're still answering the original question. It's what a careful scientist would do, just delegated. In the repo, review-ai-paper does this for research papers, mine or anyone else's: it pulls the cited sources to check they really say what's claimed, audits the code, and builds a claim ledger before writing the review. And organize-research-project writes the isolation rule down.

## 8. Studies and the core
That isolation rule scales up to the whole project, which is what organize-research-project is really about. Research means pushing many thrusts in different directions, and most of them fail. So each one lives in its own study, an isolated folder, and my AGENTS.md tells every agent to stay inside its own study. Once an agent picks up a wrong approach, it tends to follow it forever; isolation stops that from spreading, and keeps exploration creative. But pure isolation means reinventing the wheel. So there's also an established core of theory and code. A result gets in only through promotion gates: an independent audit, plus integration, meaning shared notation, tests, and clean interfaces. And I approve every promotion myself. That core is where the signal is high. Future studies can build on its theorems and its code, and when I read something there, it's worth reading properly. The skill keeps three questions separate: is a result true, has it been checked, and has it been adopted. And it comes with templates for AGENTS.md and for each study.

## 9. Make them explain it to you
The last filter is your own head. Even good results are hard to read, because model output is full of compressed notation: dozens of new symbols to say in a line what would take pages. So I have a skill whose only job is to make the model teach me: teach-technical-math. It teaches a paper, or a report the agents wrote, one block at a time, with every symbol defined before it's used. And when I'm confused, it doesn't add a one-line patch; it rebuilds the whole explanation. The general lesson: write skills that teach the model how to talk to you.

## 10. Conclusion: the repo
So, to wrap up. The problem was a pile of output you can't check, and every trick was a filter. Pose the right question: investigate-conjectures, then solve-math-rigorously. Check it with fresh, isolated auditors: review-ai-paper. Promote only what survives into a trusted core: organize-research-project. And make the result readable: teach-technical-math. They're all in the repo, as plain markdown. They're written for Codex, and the same SKILL.md format works in Claude Code. Each one stands on its own, so take just the one you need. None of this is final. It's hacky, it's what the transition looks like for me right now, and there's a lot of room to improve. So take whatever's useful, break what doesn't, and please tell me your own tricks. Thanks.
